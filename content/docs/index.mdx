# Emunium documentation

Emunium reads the page through a browser extension and acts through the operating system. Use Python locators to find elements, then move the desktop cursor, click, and type through native input.

Start an installed Chrome, Edge, Brave, or Chromium, or connect to a prepared Firefox-family profile, including Camoufox. The guides below include the full reference from the original README.

## How it works

The extension finds elements and reads page state. Native input handles the mouse and keyboard. Before a click, Emunium checks that the page sees the pointer over the intended element. Typing checks keyboard focus.

| Task | How Emunium handles it |
| --- | --- |
| Find an element | Extension-based CSS, XPath, text, role, label, or test-ID lookup |
| Click or type | OS input: Win32 on Windows, X11 XTest on Linux, pyautogui on macOS |
| Wait for a result | Element conditions, navigation waits, response waits, and assertions |
| Keep a profile | A persistent profile or `Browser.connect()` |
| Automate the desktop | Image matching and optional OCR in standalone mode |

<Notice title="Input and browser setup are different paths">
Page actions do not use CDP or WebDriver. Chrome launch does use a private debugging pipe to install the extension, and Emunium maintains a local bridge. The original README's opening "No CDP" line must be read with its detailed browser-setup section, not as a claim that no CDP is used anywhere. See [Browsers](/docs/browsers/) and [Connect to your own browser](/docs/connect/).
</Notice>

## Before you run

Native input moves the real cursor and uses the desktop keyboard. Keep the browser visible and focused, and do not use the mouse or keyboard while the script runs. Headless sessions support DOM operations, not native input. Iframes are not supported.

Read [Limitations](/docs/limitations/) for platform requirements and [Running in parallel](/docs/parallel/) before adding workers.
